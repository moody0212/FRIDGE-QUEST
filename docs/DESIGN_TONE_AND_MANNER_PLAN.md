# FRIDGE QUEST 전체 사이트 톤앤매너 수정 계획서

작성일: 2026-08-27

## 1. 문서 기준과 전제

- 현재 저장소 루트와 하위 경로에서 `디자인.md` 파일은 확인되지 않았다.
- 따라서 이 계획은 현재 구현된 FRIDGE QUEST 화면을 기준선으로 작성한다.
- 이 기준선으로 공개 랜딩페이지(`/`)와 실제 서비스(`/quest`)를 분리해 구현했으며, 랜딩의 CTA는 `/quest`로 연결한다.
- 실제 디자인 수정에 착수하기 전 `디자인.md` 또는 동일한 역할의 디자인 가이드를 다시 확인하고, 아래의 색상·타이포그래피·컴포넌트 원칙을 해당 가이드에 맞게 최종 매핑한다.
- 랜딩페이지 구현 시 기존 서비스 UI와 AI 프롬프트, 레시피 생성 및 검증 로직은 변경하지 않는다.

## 2. 목표

FRIDGE QUEST의 기존 핵심 인상인 따뜻함, 친근함, 게임성을 유지하면서 입력부터 로딩, 결과, 오류 상태까지 한 서비스처럼 일관된 시각 언어를 적용한다.

핵심 방향은 다음과 같다.

1. 따뜻한 냉장고 구조대: 크림색 바탕과 초록색 구조 테마를 중심으로 유지한다.
2. 재미있지만 신뢰할 수 있는 안내: 게임 요소는 보상과 상태 전달에 사용하고, 레시피와 안전 안내는 명확하게 표현한다.
3. 모바일 우선: 작은 화면에서 정보 위계와 터치 영역을 우선 정리한다.
4. 기능 보존: 디자인 변경으로 입력, 로딩, AI 응답 검증, 구조 판정, EXP 계산, 재추천 동작이 달라지지 않게 한다.

## 3. 현재 화면 진단

### 유지할 강점

- 크림색 배경, 초록색 포인트, 노란색 보상 컬러가 서비스 주제와 잘 맞는다.
- 둥근 카드, 칩, 캐릭터가 친근한 게임형 서비스 인상을 만든다.
- 입력 → AI 분석 → 퀘스트 결과로 이어지는 단일 화면 구조가 모바일 MVP에 적합하다.
- `SectionCard` 등 일부 공통 컴포넌트가 있어 일관성 개선의 기반이 있다.

### 정리가 필요한 부분

- 카드별 그림자 깊이와 테두리 표현이 개별 클래스에 흩어져 있어 화면마다 무게감이 달라질 수 있다.
- 이모지와 아이콘의 역할 및 크기 규칙이 일정하지 않아 정보 위계가 흔들릴 수 있다.
- 제목, 설명, 보조 문구, 상태 문구의 크기와 굵기 기준을 더 명확히 나눌 필요가 있다.
- 입력과 결과 화면에 일회성 스타일이 반복되어 향후 수정 시 시각적 불일치가 생길 가능성이 있다.
- 결과 화면은 정보량이 많으므로 카드 간 간격과 중요도 순서를 일관되게 조정할 필요가 있다.
- 로딩·성공·실패 상태의 전환이 같은 서비스 흐름으로 느껴지도록 모션과 상태 색상의 규칙이 필요하다.

## 4. 디자인 시스템 정리 원칙

### 색상

- 배경: 기존 크림 계열을 화면의 기본 바탕으로 사용한다.
- 주요 행동과 구조 가능 상태: 초록 계열을 사용한다.
- 보상과 강조: 노란 계열을 제한적으로 사용한다.
- 구조 실패와 오류: 빨강 계열을 사용하되, 구조 실패가 폐기나 위험을 뜻하는 것으로 오해되지 않도록 설명 영역은 중립적인 톤을 함께 사용한다.
- 비활성 상태: 배경과 충분히 구분되는 중성 회색을 사용한다.

### 타이포그래피

- 브랜드 및 큰 제목: 현재의 `Jua` 계열을 유지한다.
- 본문과 입력: 현재의 `Noto Sans KR` 계열을 유지한다.
- 화면 제목, 섹션 제목, 본문, 보조 설명, 캡션의 단계별 크기·굵기·행간을 토큰으로 정리한다.
- 긴 한국어 문장이 작은 모바일 화면에서도 읽히도록 본문 행간과 줄바꿈을 점검한다.

### 형태와 깊이

- 카드 모서리, 칩 모서리, 버튼 모서리의 사용 기준을 구분한다.
- 그림자는 기본 카드, 선택 카드, 강조 카드의 3단계 이내로 단순화한다.
- 테두리 두께와 색상을 상태별로 통일한다.
- 장식용 그림자가 텍스트 대비나 터치 영역을 방해하지 않도록 한다.

### 아이콘과 캐릭터

- 캐릭터는 첫 진입과 AI 분석 등 핵심 감정 전환 지점에 집중해서 사용한다.
- 이모지는 게임 상태를 빠르게 인지시키는 용도로 유지하되, 동일한 의미에는 동일한 아이콘을 사용한다.
- 기능 버튼에는 접근 가능한 텍스트 라벨을 유지한다.

## 5. 단계별 수정 계획

### 단계 0. 디자인 기준 확정

- `디자인.md` 존재 여부와 최신 버전을 확인한다.
- 문서에서 색상, 폰트, 여백, 모서리, 그림자, 아이콘, 캐릭터 사용 원칙을 추출한다.
- 현재 구현과 가이드의 차이를 표로 정리하고 변경 우선순위를 확정한다.
- 가이드와 현재 기능 요구사항이 충돌하면 기능과 접근성을 우선하고 시각적 대안을 정한다.

### 단계 1. 전역 디자인 토큰 정리

- `app/globals.css`의 색상을 역할 기반 변수로 정리한다.
- 타이포그래피 단계, 모서리, 그림자, 포커스 링의 공통 기준을 정의한다.
- 기존 클래스와 호환되는 방식으로 적용해 한 번에 화면이 깨지지 않도록 한다.
- `app/layout.tsx`의 배경색, 테마 색상, 폰트 설정이 디자인 기준과 일치하는지 확인한다.

### 단계 2. 공통 컴포넌트 스타일 통일

- `SectionCard`를 기준으로 기본 카드의 테두리, 그림자, 간격을 통일한다.
- 선택 칩, 재료 칩, 상태 칩의 공통 규칙을 정리한다.
- 기본 버튼, 보조 버튼, 재시도 버튼의 상태별 스타일을 통일한다.
- hover, active, focus-visible, disabled 상태를 모바일과 키보드 환경 모두에서 확인한다.

### 단계 3. 화면 흐름별 적용

1. 시작 및 입력 영역
   - 히어로, 재료 입력, 기본 재료 선택, 조리시간 카드의 정보 위계를 정돈한다.
   - 기존 입력 방식과 항목 구성은 유지한다.
2. AI 분석 로딩 영역
   - 단계 카드의 완료, 진행, 대기 상태를 전역 상태 색상과 모션 규칙에 맞춘다.
   - 실제 AI 처리 시간과 상태 전환 로직은 변경하지 않는다.
3. 결과 영역
   - 요리명, 구조 결과, 실패 이유, 조리법, 별도 활용 안내, EXP, 재추천 버튼의 중요도 순서를 시각적으로 명확히 한다.
   - 기존 `곁들임 & 별도 활용 안내`의 데이터와 기능은 유지한다.
4. 오류 영역
   - 오류와 구조 실패가 서로 다른 의미로 보이도록 상태 표현을 분리한다.
   - 기존 재시도 흐름은 유지한다.

### 단계 4. 반응형과 모션 보정

- 320px, 375px, 430px 폭에서 텍스트 잘림, 가로 스크롤, 터치 영역을 확인한다.
- 넓은 화면에서도 모바일 중심 콘텐츠 폭과 여백이 자연스럽게 보이도록 한다.
- 결과 등장과 로딩 상태 전환은 짧고 부드럽게 유지한다.
- `prefers-reduced-motion` 환경에서는 회전과 이동 효과를 줄이거나 제거한다.

### 단계 5. 품질 검증

- 초기 화면, 입력 완료, 로딩 3단계, 전체 구조 가능, 일부 구조 실패, AI 오류, 재추천 상태를 각각 확인한다.
- 색 대비, 키보드 포커스, 버튼 라벨, 폼 레이블을 점검한다.
- 타입 검사, 린트, 프로덕션 빌드를 실행한다.
- 주요 모바일 폭의 스크린샷을 비교해 의도하지 않은 레이아웃 변화를 확인한다.
- AI 프롬프트, 구조 판정, EXP, 별도 활용 안내 데이터가 변경되지 않았는지 회귀 테스트한다.

## 7. 변경하지 않을 범위

- AI 프롬프트와 응답 스키마
- 레시피 선택 및 생성 로직
- `allIngredients`, `rescuedIngredients`, `failedIngredients` 판정과 검증
- EXP 계산과 표시 데이터
- 다른 요리 추천 및 우선 구조 로직
- `곁들임 & 별도 활용 안내`의 기능과 데이터 연결
- API 경로, 환경 변수, 배포 설정
- DB, 로그인, 회원가입, 결제, 새 페이지

## 8. 완료 기준

- 입력, 로딩, 결과, 오류 화면이 동일한 색상·타이포그래피·카드·상태 규칙을 사용한다.
- 기존 기능과 사용자 흐름이 디자인 수정 전과 동일하게 동작한다.
- 320px 이상의 주요 모바일 폭에서 가로 스크롤과 중요한 텍스트 잘림이 없다.
- 키보드 포커스가 식별 가능하고 주요 텍스트의 대비가 충분하다.
- 모션 감소 설정을 존중한다.
- 타입 검사, 린트, 빌드 및 핵심 상태 회귀 검증을 통과한다.
- 최종 구현 전에 `디자인.md`와의 매핑 결과가 계획서 또는 작업 기록에 반영된다.

## 9. 권장 작업 단위

1. 디자인 기준 확정 및 토큰 정리
2. 입력 화면과 공통 컴포넌트 적용
3. 로딩·결과·오류 화면 적용
4. 반응형·접근성·회귀 검증

각 작업 단위가 끝날 때 화면 상태별로 확인하고 커밋을 분리하면 디자인 변경의 원인과 영향 범위를 추적하기 쉽다.

## 10. 주요 위험과 대응

- 디자인 문서 누락: 실제 수정 전에 파일 위치와 최신 버전을 확정한다.
- 대규모 일괄 변경으로 인한 회귀: 토큰 → 공통 컴포넌트 → 개별 화면 순서로 적용한다.
- 기존 사용자 변경과 충돌: 현재 작업 트리의 변경 파일을 보존하고 디자인 관련 변경만 분리한다.
- 게임성 과다로 인한 가독성 저하: 장식보다 정보 위계와 조리 안내의 신뢰성을 우선한다.
- 모바일 높이 증가: 카드 내부 여백과 반복 설명을 점검하되 정보나 기능을 삭제하지 않는다.
