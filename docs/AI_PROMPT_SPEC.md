## 1. 프롬프트 핵심 비즈니스 규칙 (10대 레시피 품질 & 사고 단계 룰)

1. **레시피 결정 전 재료 역할 내부 판단 (Step A)**:
   - 레시피 이름 생성 전 입력 재료의 역할을 판단 (단백질/주재료, 베이스/곡물류, 소스/양념, 조리완료 음식 등).
2. **사고 순서 고수 (Step A ~ Step E)**:
   - 재료 역할 파악 → 구조 1순위(🟡) 확인 → 요리 형태 후보(랩, 롤, 퀘사디아, 토스트, 전, 덮밥, 구이, 찌개, 볶음 등) 판단 → 최적 요리 1개 결정 → 레시피 구성.
3. **"볶음" 습관적 기본값 사용 절대 금지**:
   - 습관적으로 "○○ 볶음"을 생성하는 편향을 금지한다.
   - 또띠아, 식빵, 샐러드, 소스류, 조리완료 음식은 "볶음" 대상에서 제외하고 랩/롤/토스트/퀘사디아/전 등으로 다변화한다.
4. **소스 및 양념의 주재료 취급 금지**:
   - 스리라차 소스, 마요네즈 등의 소스 이름을 "또띠아 스리라차 소스 볶음"처럼 요리명 주재료로 결합하지 않는다. 소스는 레시피 내부의 양념으로 활용한다.
5. **현실적 조리 가능성 및 품질 우선 (extraNeeded 허용)**:
   - 보유 재료만으로 괴상한 요리를 만드는 대신, 필수 재료(계란 등)를 `extraNeeded`에 추가하여 실제 먹을 수 있는 요리를 추천한다.
6. **자연스러운 요리명 생성**:
   - 입력 단어의 단순 결합 금지. '매콤 계란 또띠아롤', '김치 치즈 퀘사디아', '삼겹살 양파구이' 등 실제 음식명으로 생성.
7. **재추천(Reroll) 시 조리 형태 다변화**:
   - `excludeDish`를 통해 직전 추천과 다른 조리 형태(볶음 → 전 → 덮밥 → 랩 등)를 선택한다.
8. **요리 형태에 맞춘 조리법 작성**:
   - 랩(펴기→속재료→말기), 전(반죽→부치기), 덮밥(볶기→밥 올리기) 등 조리 형태에 맞는 5단계 구성.
9. **한국어 조사 괄호 표기 금지**:
   - `(을/를)`, `(이/가)` 등 괄호 표기를 금지하고 한국어 받침 연산(`attachJosa`)에 맞는 정갈한 문장 작성.
10. **출력 데이터 정합성**:
   - `rescueUsed`, `basicUsed`, `extraNeeded`, `tip`, `steps` 데이터 일관성 준수.

## 2. 입출력 스키마 (TypeScript & JSON)

### 2.1 Request Payload
```typescript
export interface QuestApiRequest {
  basics: string[];
  items: {
    name: string;
    status: 'fresh' | 'soft' | 'bad';
  }[];
  cookTime: '10' | '20' | 'any';
  excludeDish?: string; // 직전 추천 요리 (조리 형태 다변화용)
}
```

### 2.2 Response Payload
```typescript
export interface QuestApiResponse {
  rescueTarget: string;      // 주 구조 대상 재료명 (예: "또띠아")
  dish: string;              // 추천 요리명 (예: "매콤 계란 또띠아롤")
  time: string;              // 예상 조리시간 (예: "약 15분")
  rescueUsed: string[];      // 실제 레시피에 사용된 냉털 재료
  basicUsed: string[];       // 실제 사용된 기본 재료
  extraNeeded: string[];     // 추가 필요 재료 (없으면 [])
  steps: string[];           // 요리 형태에 맞춘 최대 5단계 조리법
  tip?: string;              // 소스 활용법 또는 곁들임 팁
  warningMessage?: string;   // 🔴 재료 관련 안전 경고 문구
  exp: number;               // 보상 경험치 (80 ~ 150)
}
```
